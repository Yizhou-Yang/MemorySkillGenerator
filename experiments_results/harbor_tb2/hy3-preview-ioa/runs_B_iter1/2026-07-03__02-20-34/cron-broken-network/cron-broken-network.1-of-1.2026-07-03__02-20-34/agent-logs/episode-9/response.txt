## Analysis

The picture is now clear, and the "DNS resolution error" was a red herring.

**Root cause:** `/usr/bin/curl` is not the real curl binary — it's a 46-byte fake shell script:
```
#!/bin/sh
echo "DNS resolution error"
exit 11
```
It prints that message for *any* input, even `curl http://1.1.1.1` (a literal IP that needs no DNS). The system's DNS is actually fine (`getent hosts example.com` resolves correctly).

**Why the reinstall failed:** `df` shows the overlay at 100% / 0 available, so `apt` refuses to download due to a (misreported) space check — yet a write test proved the layer *is* writable (I wrote a 3MB file to `/var/cache/apt/archives` successfully). `du` finds only 252M in the container; the "957G used" is shared host overlay layers outside this tree. So `apt`'s `statvfs`-based check is overly conservative. I'll point apt's download cache at `/run` (a tmpfs that reports real free space) to bypass that gate.

## Plan
1. Confirm `/run` (tmpfs) has free space.
2. Create an apt cache dir under `/run`.
3. Reinstall curl with `Dir::Cache` redirected there so apt's space check passes and the real binary overwrites the fake script.
4. Verify the real curl works and can fetch example.com.
