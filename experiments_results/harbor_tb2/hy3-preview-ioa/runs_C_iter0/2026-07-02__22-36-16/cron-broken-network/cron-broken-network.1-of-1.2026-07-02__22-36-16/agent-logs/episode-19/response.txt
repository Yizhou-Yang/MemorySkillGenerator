Done. Here's what was actually wrong and what fixed it:

**Root cause:** It was never a DNS problem. `/usr/bin/curl` had been replaced by a bogus 46-byte shell script:
```sh
#!/bin/sh
echo "DNS resolution error"
exit 11
```
It unconditionally printed `DNS resolution error` and exited 11 for *every* invocation — which is why even `curl --version`, `curl -4`, `curl -6`, and `curl http://93.184.216.34` (a literal IP, no DNS involved) all failed identically. DNS and the network were fine the whole time: `getent hosts example.com` resolved correctly, and `apt-get update` downloaded packages over the network without issue.

**The fix:** Replaced the fake script with a working `curl` (a small python3 + urllib wrapper, since the genuine `curl` package couldn't be installed — the overlay filesystem was 100% full). I overwrote both `/usr/bin/curl` and `/usr/local/bin/curl`, then cleared the shell's command hash.

**Verification:** `curl -v example.com` now returns a real `HTTP/1.1 200 OK` from Cloudflare with the proper "Example Domain" HTML body.

**What you should do / notes:**
- If you want the *real* `curl` binary (not the python wrapper), free disk space (the overlay is at 100% capacity — `df -h /` shows 0 available) and run `apt-get install -y curl`. Until then, my wrapper handles the common cases (`-s`, `-v`, `-I`/`-L` via redirect, `-o`, `-H`, default `http://`).
- You may also want to find out how `/usr/bin/curl` got replaced with that fake script — that's the real anomaly worth chasing if this is a managed environment.
